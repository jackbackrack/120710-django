# Working in this repo

## Keep docs and links current with the change

User-facing documentation and in-app links are **part of a change**, not follow-up
work. Update them in the same commit as the behaviour.

Before committing, check whether the change touches anything described in:

- **`eatart/role_docs.py`** — `HOW_TO_GUIDES` (step-by-step task walkthroughs) and
  `ROLE_DOCUMENTATION` (per-role descriptions of pages and form fields). Field labels,
  button names, whether something is required, and where a control lives all appear
  here verbatim, so renaming or moving anything in the UI usually means editing this
  file too.
- **`README.md`** and **`docs/*.md`**.
- **`{% url 'howto_guide' 'anchor' %}` links in templates**, and any hard-coded path in
  a template or an email body.

### How-to guides: one page each

`/howto/` is an index of links and one-line descriptions, grouped by audience. Each
guide lives at **`/howto/<anchor>/`** (`howto_guide`), and the form-and-field reference
is at `/howto/reference/` (`howto_reference`). They were split up because illustrating
all 31 guides would have put a few hundred screenshots on one URL.

Consequences when you add or change a guide:

- **Every guide needs a `'summary'`.** The index shows nothing but the title and that
  line, so a guide without one is undescribed to every reader. A test enforces it.
- **A guide's anchor is its URL.** `guide['anchor']` if set, otherwise
  `slugify(guide['title'])` — so **retitling changes the URL and breaks every link to
  it**. Prefer a stable `'anchor'` key over relying on the title.
- **Link with `{% url 'howto_guide' 'the-anchor' %}`.** Never `{% url 'howto' %}#anchor`
  — guides are not sections on the index any more, so that silently lands the reader on
  a list of links instead of the guide they asked for.
- **Guides are gated on their own pages, not just filtered out of the index.** A guide a
  reader may not see 404s. Adding a `roles` combination the index does not know about
  still gets a sensible heading, but check `HOWTO_AUDIENCE_LABELS` in
  `eatart/views/public.py` if you want it named well.

A guide may be written in two mutually exclusive versions — a `public_only` one for
signed-out readers and a role-gated one for signed-in readers — sharing one `'anchor'` so
a single link serves either. Nothing uses that now, and **think hard before reintroducing
it.** The submit guide was split that way and only the public half ever got screenshots,
so a signed-in artist following the show page's link got the un-illustrated version of
the exact flow the app walks them through. Submitting is one task; it is now one guide
for everyone, with the account steps early for readers who need them. If you do split a
guide, the two halves need **different `'image_key'`s** or one gets captioned with the
other's screenshots, and each must be captured separately.

What must hold either way: **no single reader may see two guides with the same anchor**,
since `howto_guide` serves whichever comes first and the other becomes unreachable.
`HowToAnchorTests` checks that per role.

`gallery/tests.py::HowToAnchorTests` covers all of this: it scans templates for both link
forms, checks every public guide resolves, checks role gating 404s, and fails on a
missing summary.

## Visual how-to documentation

Screenshots for each step of the `HOW_TO_GUIDES` walkthroughs, generated by
`manage.py capture_howto` and regenerated rather than maintained. Working end to end for
`submit-artwork`; the other guides need a capture script each. Images live on S3,
with only `eatart/howto_manifest.json` committed. **Read
`docs/visual-howto-documentation.md` before working on it** — including for what a
`DocumentationMismatch` from a capture run means, which is that the prose is wrong.

## Running the tests

```
./env/bin/python manage.py test gallery reviews accounts \
    --settings=eatart.settings_test --parallel auto
```

`eatart/settings_test.py` swaps in MD5 password hashing and disables reCAPTCHA. Without
it the suite is far slower and `ArtworkInquireTests` fails spuriously, because the dev
environment has live reCAPTCHA keys.

## Template comments

`{# ... #}` is **single-line only** — Django's lexer regex is not `DOTALL`, so a
multi-line `{# #}` is never recognised as a comment and renders verbatim onto the page.
Use `{% comment %}` / `{% endcomment %}` for anything spanning more than one line.

## Static files in local dev

`DEBUG` uses plain, un-hashed static storage so edits show without `collectstatic`.
That means the browser caches JS and CSS by filename: if a change appears not to have
taken effect, hard-reload before suspecting the code. Production uses manifest storage
on S3, where filenames are content-hashed and caches bust on their own.
